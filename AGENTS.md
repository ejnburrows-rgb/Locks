# Working rules

1. Treat `main` as the authoritative application branch.
2. Read `README.md` and `docs/STATUS.md` before changing business-facing content.
3. Never invent licensing, insurance, response times, warranties, pricing, testimonials, review sources, service coverage, or technician identities.
4. Never claim a quote, dispatch, phone call, email, or other external action completed unless the application actually performed it.
5. Prefer durable owned/licensed images over temporary generated-image URLs.
6. Run `npm run lint` and `npm run build` before release.
7. Use short-lived branches for active work and remove them after merge.
8. Do not delete `gh-pages` until its deployment purpose is explicitly verified.

## Scope and current owner directive

This AGENTS.md applies **only to this repository**. The current owner request is **source-of-truth and instruction organization only**, not product implementation, release or agent dispatch. Resume product work only on a later explicit instruction. Historical chats, audits and external dashboards do not override the latest scoped owner decision or verified code.

## Delivery and protection rules

- Start with current GitHub main/default branch, existing related PRs and project requirements. Reuse work, do not duplicate agents, branches, controllers, audits or planning files.
- One assignment has a bounded outcome. In an authorized work session, handle ordinary engineering decisions; a blocked operation does not stop other safe, independently authorized work. Never claim background work without direct session evidence.
- Evidence is exact revision, relevant tests, independent material review and real visual proof when behavior changes. Do not equate coded, merged and deployed. No invented progress or active agent counts.
- Use a focused branch/PR and respect applicable branch protection, independent review and exact-change merge authorization. No self-approval, force push or destructive cleanup.
- A default-branch merge **may publish production**; verify this repository's actual deploy configuration and obtain separate release authorization before merging. Never enable auto-merge/deploy just to clear a queue.
- Keep secrets and personal data out of code and reports. No spending, security/access changes, real-data deletion or production release without applicable permission.
- GitHub Actions or a paid runner is not an assumed prerequisite. Use available direct/local checks; treat unrelated repository CI or Vercel failures as scoped to that repository.
- Report **STATUS / RESULT / PROOF / WHAT REMAINS** with a link to each real change. Do not stop merely for routine owner approval or claim a product feature was finished by documentation work.
